# 卦眼 2.0 · 六爻排卦、关系可视化、自定义规则与卦例复盘总开发计划

> **目标平台**：Android  
> **开发框架**：Flutter + Dart  
> **屏幕方向**：仅手机竖屏  
> **运行方式**：本地优先、离线可用  
> **UI 策略**：卦眼独立设计，不依赖 XYUI；未来仅在有成熟成品且确有必要时局部替换  
> **核心定位**：排卦工具 + 关系可视化 + 关系审计 + 自定义规则 + 笔记 + 卦例复盘 + AI 分析材料导出

---

# 0. 产品总目标

卦眼 2.0 不做单纯排盘软件，也不直接做“自动断卦大师”。

核心解决的问题是：

> **传统六爻解卦严重依赖人工逐条扫盘，冲、合、生、克、动变、墓库、月日、取象等信息容易漏看。卦眼负责把这些结构化事实自动计算、可视化、列举、记录并导出。**

完整工作闭环：

```text
确定起卦时间
↓
录入六爻
↓
自动排盘
↓
自动计算基础关系
↓
应用用户自定义象义规则
↓
审卦连线可视化
↓
关系总账查漏
↓
逐条关系写笔记
↓
保存为卦例
↓
后验补充结果
↓
复盘
↓
生成可复制文字 / AI 分析材料
```

# 1. 已拍板技术选型

## 1.1 客户端

继续采用：

```text
Flutter
+

+

```

不迁移 Kotlin、Capacitor、React Native 等其他技术。

- 已有 Flutter 开发基础

```text

= 不等待 XYUI
```

未来如果 XYUI 某个组件已经成熟，且明显优于卦眼当前实现：

```text

```

例如：

- Dropdown
- Checkbox
- Badge
- Button

但：

- 不把 XYUI 作为依赖前提
- 不为未来 XYUI 提前大规模抽象
- 不阻塞卦眼当前开发

# 22. Relation 重算数据保护

这是强制 Gate。

关系重新计算后：

> **绝对不能静默丢失用户笔记。**

必须使用稳定匹配身份，例如：

```text
caseId
+
ruleId
+
sourceSemanticId
+
targetSemanticId
+
subtype
```

重算后：

- 相同关系复用旧笔记
- 新关系新增
- 消失关系不得直接删除笔记
- 需要明确迁移策略

# 25. 自定义规则 JSON

Schema：

```text
guayan-rule@0.1
```

示例：

```json
{
  "schemaVersion": "guayan-rule@0.1",
  "id": "custom-home-door-line3",
  "name": "住宅 · 三爻为门户",
  "enabled": true,
  "category": "home",
  "packId": "home-symbols",
  "priority": "normal",
  "matchMode": "all",
  "conditions": [
    {
      "field": "question.category",
      "operator": "equals",
      "value": "home"
    },
    {
      "field": "line.position",
      "operator": "equals",
      "value": 3
    }
  ],
  "outputs": [
    {
      "type": "add_semantic",
      "values": [
        "家门",
        "门口",
        "门户"
      ]
    }
  ],
  "description": "住宅类占问中，三爻可取象为家门或门户附近。",
  "conflictPolicy": "coexist"
}
```

# 58. 产品最终边界

卦眼负责：

> **把卦排对，把关系找全，把用户自己的规则套进去，把笔记保存好，把材料整理完整。**

人负责：

> **判断这些事实在具体事情中意味着什么。**

AI 可以负责：

> **读取卦眼已经结构化好的材料，辅助进一步分析。**

这三者职责分离，是卦眼 2.0 最重要的架构原则。

# 59. 最终一句话

**卦眼 2.0 = 六爻结构化工作台。**

它不以“替人算卦”为核心，而以：

> **不漏关系、可视化关系、自定义理论、记录经验、复盘验证、结构化输出**

作为真正的产品价值。
